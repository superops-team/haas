# Review Spec

## Contract

使用本 skill 时，必须围绕当前 spec/方案完成端到端校验与落地梳理，保证输出：

- 明确指出问题、影响、整改建议与优先级，避免泛泛评价。
- 覆盖逻辑一致性、可落地性、语义清晰性、SDD/TDD 适配、最小化实现、兼容性、存量影响、运行风险、可行性、扩展性与架构统一性。
- 基于问题整改结果，给出可执行的完善方案、分层任务拆解、测试规划与开发排期。
- 优先小而高效的改动，警惕过度设计，保持整体架构风格统一、逻辑连贯。

## Phases

1. **定位当前 spec**
   - 优先使用用户明确给出的 spec/PRD/SDD/TDD 文件或文本。
   - 若用户未指定，搜索当前仓库中与当前分支、当前需求、`spec`、`prd`、`openspec`、`sdd`、`tdd` 相关的文件。
   - 若仍无法定位，先询问用户当前 spec 的位置或内容，不要凭空评审。

2. **建立上下文基线**
   - 梳理背景、目标、范围、非目标、约束、依赖、关键术语、用户/系统边界。
   - 标记上下文断裂、前后矛盾、范围漂移、遗漏的前置假设。

3. **逐项问题校验**
   - 查：上下文连贯、空洞表述、歧义点、大模型语义偏差、SDD/TDD 阻碍。
   - 查：最小化实现、边界划分、可测试拆解、向下兼容、存量业务破坏性影响。
   - 查：功能失效/运行异常风险、实际落地可行性、扩展性成本、过度设计。
   - 查：是否小而高效、是否让代码逻辑更优雅直观、是否保持架构风格统一。

4. **整改与完善方案**
   - 对每个问题给出可操作的改写或方案调整建议。
   - 将整改后的方案组织为：目标、范围、非目标、设计原则、核心流程、接口/数据/模块边界、兼容策略、风险控制、验收标准。
   - 对不确定项单独列为待确认问题，不要混入已确定方案。

5. **落地计划输出**
   - 分层任务拆解：按基础设施/数据模型/API/业务逻辑/迁移兼容/测试/文档等层次拆分。
   - 测试规划：覆盖单元测试、集成测试、回归测试、兼容性测试、异常/边界场景、必要的 TDD 红绿重构路径。
   - 开发排期：给出阶段、关键里程碑、依赖关系、风险缓冲与可交付物。

## Output Format

```markdown
# Spec Review Report

## 1. 总体结论
- 可行性：高/中/低
- 最大风险：...
- 推荐方向：...

## 2. 问题清单
| 优先级 | 维度 | 问题 | 影响 | 整改建议 |
|---|---|---|---|---|

## 3. 整改后的完善方案
按目标与范围、非目标、设计原则、核心方案、兼容与风险控制、验收标准组织。

## 4. 分层任务拆解
| 层级 | 任务 | 交付物 | 依赖 | 优先级 |

## 5. 测试规划
| 类型 | 覆盖点 | 关键用例 | 执行阶段 |

## 6. 开发排期
| 阶段 | 时间/顺序 | 工作项 | 风险与缓冲 | 验收物 |

## 7. 待确认问题
- ...
```

## Anti-Patterns

- 不要只给“看起来没问题”“建议补充细节”等空泛结论。
- 不要把问题清单和整改后方案混在一起，导致执行者无法区分现状与目标态。
- 不要默认引入复杂架构、重型框架或大范围重构；必须优先小步、轻量、可测试。
- 不要忽略存量业务、向下兼容、迁移路径和回滚策略。
- 不要输出无法验证的验收标准；每条关键结论都应可执行、可测试或可确认。
